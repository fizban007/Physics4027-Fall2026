What is this course?

Walk the four petals. Numerical analysis: the algorithms and their failure modes. Software engineering: you implement, test, and version-control real code. Physics applications: every method is aimed at a physical system. Agentic AI: you will direct AI agents to do much of the building, and learn to verify what they build. No other course on campus sits at this intersection.

What this course is

  • A course on using numerical algorithms to solve physics problems you cannot solve on paper.
  • A course where you implement the algorithms — not just call a black-box library. We will not shy away from nitty-gritty implementation details.
  • A course where you learn cutting-edge agentic AI and use it to get things done. AI use is not just permitted — the course is built assuming you use it for most of the coursework.
  • A challenging course culminating in three projects involving complex physics.

What this course is not

  • An algorithms course in the CS sense — no sorting, no AVL trees, no dynamic programming. Take a proper data structures course for that.
  • A traditional physics course. We borrow examples from every branch of physics but cover none in depth; you either know it already, or you learn just enough.
  • Career prep for software development. But what you learn here is very valuable for a career in quantitative science or engineering.

No prior programming experience is required — the first weeks bring everyone up to speed.

Why agentic AI?

  • A modern AI agent can write a working ODE solver faster than you can read the assignment. It is the future of programming and computational physics in general.
  • That does not make numerical methods obsolete. Implementation has never been the real bottleneck. It's at knowing what to do, verifying the implementation, and interpreting the physics.
  • This semester: the agent may write your code — you own the predictions, the interpretation, and the diagnosis when it is wrong.
  • To facilitate this, oral presentations are an integral part of the course.
This is the honest rationale for the course design. Pretending agents don't exist makes take-home artifacts meaningless as assessment; embracing them means the course must teach and grade the skill of directing and verifying them.

Floating point numbers

How computers represent the real line and where it breaks

A finite budget of bits

There are uncountably many real numbers; a float has 32 bits — at most $2^{32}$ distinct values to cover them all.

The solution is binary scientific notation: store a sign, a fraction, and an exponent. The "fraction" is also called "significand" or "mantissa".

$x = (-1)^s \times 1.f \times 2^{\,e-127}$

The implicit leading 1 in the fraction is a favorite quiz question. Note the exponent bias. Double precision: 11 exponent bits, 52 fraction bits, bias 1023.

The C++ floating point types

TypeBits∼Decimal digitsTypical use
float327 graphics, games, ML
double6416 scientific computing's workhorse
long double80/128≥18 occasional extra headroom

Machine learning pushed the other way: fp16, bf16, fp8, even fp4 — trading accuracy for speed and memory.

Not every decimal exists in binary

$0.1$ has no finite binary representation — just as $1/3$ has none in decimal. The computer stores the nearest representable number instead.

Code


double a = (1.0 - 0.1) - 0.9;
double b = (1.0 - 0.05 - 0.05) - 0.9;
std::cout << a << std::endl;
std::cout << b << std::endl;

Output


0
-1.11022e-16

Rounding makes arithmetic non-associative: $(a+b)+c$ need not equal $a+(b+c)$.

Machine epsilon and ULP

Unit in the Last Place (ULP): the distance between two adjacent floating point numbers — the change from flipping the last bit of the fraction.

The ULP scales with the exponent, so we usually quote the ULP at exponent 0. That number is the machine epsilon: the relative precision of the format.

1 ULP is the best accuracy any single floating point operation can promise. Expecting more from a calculation is expecting magic.

Catastrophic cancellation

Subtracting two nearly equal numbers cancels their leading digits, leaving only the trailing bits — which are rounding noise.

Code


double x = 1.0e-8;
double naive = 1.0 - std::cos(x);
double stable =
    2.0 * std::sin(0.5 * x)
        * std::sin(0.5 * x);
cout << "naive:" << naive << endl;
cout << "stable:" << stable << endl;

Output


naive: 0
stable: 5e-17

True answer: $1-\cos x \approx x^2/2 = 5\times 10^{-17}$.
The naive version is 100% wrong.

The edges of the format

  • Two zeros: $+0$ and $-0$ exist, and compare equal.
  • Infinities: 1.0/0.0 gives inf — also produced by overflow.
  • NaN (“not a number”): 0.0/0.0, sqrt(-1.0)… It propagates through arithmetic and is the only value with x != x.
  • Subnormals: when the exponent is zero, the number convention becomes slightly different, decreasing uniformly to 0.

Never compare floats directly

Test whether the difference is within a tolerance instead:

Do NOT


double a = 1.345;
double b = 1.123;
double c = a + b;
if (c == 2.468) { ... }

Do


double a = 1.345;
double b = 1.123;
double c = a + b;
double EPSILON = 1e-10;
if (std::abs(c - 2.468) < EPSILON) {
  ...
}

Choosing the tolerance is problem-dependent. We will return to this all semester.

One more ambush: integer arithmetic

  • Write 1.0 and C++ reads a double; write 1 and it reads an integer.
  • Operations between integers give integers: 1/2 is 0, not 0.5.
  • Always write numbers with a decimal point and this class of bug never happens to you.
